## 기존 패키지 관측

`profile3/virtual-stack-facts.json`은 계측한 실제 패키지 실행 `TsY7ff`의 원본 virtual-thread dump를 요약한다. initial 122,505ms, refresh 88,704ms이며 refresh의 IMPORT 24,699ms, SOURCE_PARSING 15,301ms, GRAPH_BUILD 21,948ms, TS_PARSING 21,087ms다. 계측 비용이 있으므로 출시 성능 판정에는 쓰지 않는다.

refresh job 표본에는 FILE→type 연결의 PostgreSQL 대기 9개, 소스 retain 응답 대기 6개, TS 첫 analyze 응답 대기 5개가 있다. 표본 개수는 wall time이 아니다. SOURCE_PARSING과 TS_PARSING의 저장 SQL 대기도 관측됐다. Java refresh 로그의 framework parsed 17/reused 4,479, Java analyzer parsed 51/reused phases 13,437을 확인했다. 따라서 이 후보의 지연을 Java 전체 재파싱으로 단정하지 않는다.

## 새 snapshot의 FILE 연결 계획

`GraphBuildStep.linkFileContainsTypes`가 canonical FILE의 natural key와 현재 파일 경로를 비교할 때, 새 snapshot의 통계가 없으면 넓은 snapshot index를 반복 스캔할 수 있었다.

소유권·automation marker·backend PID·후보 hash를 대조한 **합성 workload 전용** PostgreSQL 디렉터리만 새 진단 디렉터리에 COW 복제했다. 프로필의 `secrets.enc`·Keychain·계정 API에는 접근하지 않았다. 패키지의 PostgreSQL 16.15를 private Unix socket에서 실행했고 TCP listener는 만들지 않았다. source inventory digest와 복제본 일치, 원본의 사전·사후 불변, postmaster 종료를 검증했다.

최종 통계가 있는 DB에서는 `native-plan2`의 기존 SQL도 139–209ms였으며 병목이 재현되지 않았다. `native-plan3`은 트랜잭션 안에 새 snapshot과 실제 합성 파일 10,000개·노드 182,214개를 복사해 새 snapshot 통계가 없는 상태를 만들었다. 각 시나리오는 rollback했다.

| SQL | EXPLAIN ANALYZE 실행 시간 | 결과 행 | 측정 직전 load1 |
| --- | ---: | ---: | ---: |
| 기존 natural-key 연결 | 80,022.192ms | 12,836 | 3.8730 |
| 파일 ID 동일성 조건 추가 | 283.998ms | 12,836 | 3.3901 |

기존 계획은 inner scan 12,836회와 join-filter 제거 60,792,001행을 기록했다. 변경 계획은 기존 `uq_graph_nodes_snapshot_natural_key` index를 이용했다. 새 index, migration, 전역 planner 설정은 추가하지 않았다. 이는 동일 진단 DB의 실행 계획 비교이며 실제 앱 GRAPH_BUILD가 80초였다는 뜻은 아니다.

제품 변경은 `and fnode.file_id = tnode.file_id` 한 줄이다. snapshot·FILE type·canonical natural key·허용 type 조건은 유지한다. 파일 ID만 같고 natural key가 다른 FILE alias를 연결하지 않는다.

검증:

- `w23-contains-red`, `w23-contains-shape-red`: 기존 SQL의 Docker 재현 시도였지만 **둘 다 PASS하여 성능 실패를 재현하지 못했다**. 실패로 바꾸어 보고하지 않는다. 큰 비재현 fixture는 영구 시험에 남기지 않았다.
- `w23-contains-green`: 실제 PostgreSQL 대상 **3/3 PASS, 실패/error/skip 0**. `GraphPersistenceLookupPlanTest` 2개와 `GraphPersistenceRoundTripTest` 1개다.
- 새 영구 시나리오는 현재 snapshot의 canonical FILE만 CLASS/DB_ENTITY에 연결하고, 다른 snapshot·FILE alias·METHOD가 포함되지 않음을 검증한다. 기존 lookup budget와 1,200개 노드·중복 metadata·2,401개 edge round-trip도 통과했다.
- `native-plan1`의 provenance assertion 실패는 DB 복제/시작 전 발생했다. 이 실패와 두 비재현 시도, 모든 원본 계획·SQL·로그를 보존한다.

## retained source 인증의 bounded 동시 읽기

기존 retain은 최대 128개 참조의 blob을 순차적으로 열고 인증했다. `desktop/src/source-vault.cjs`는 기존 소유권·경로·파일 identity·AEAD·key ID 검사를 그대로 실행하면서 **최대 4개 읽기**만 함께 진행한다. staged write를 먼저 flush하고 기존 작업 queue 직렬화도 유지한다. 읽은 plaintext buffer는 각 작업의 finally에서 지운다.

한 읽기가 실패해도 같은 그룹의 나머지 읽기를 모두 회수한 뒤 입력 순서의 첫 오류를 반환한다. close/후속 queue 작업은 진행 중인 읽기를 추월하지 않는다. sparse 참조 배열도 기존처럼 실패하며 빈 원소를 성공으로 세지 않는다. protocol·파일 형식·hard limit·Keychain 동작은 변경하지 않았다.

검증:

- `retain-target.log`: source-vault/batch/backup/Windows abstraction/source-broker 대상 **158/158 PASS, 실패/skip 0**. Windows 패키지를 실행했다는 뜻은 아니다.
- `retain-smoke-result.json`: 실제 제품 모듈로 합성 파일 256개 stage→retain→정확한 byte readback. 마지막 ciphertext 변조 거부, close/reopen 후 정상 blob 읽기와 변조 blob 재거부 확인. 실제 Keychain 대신 합성 wrapping만 사용했다.
- `retain-early-rejection-red.log`: 조기 reject mutant가 새 drain/close 시험에서 의도대로 실패했다.
- `retain-sparse-ack-red.log`: sparse 원소를 건너뛰는 mutant가 기존 invalid-input 시험에서 의도대로 실패했다. 두 mutant는 제품 파일을 수정하지 않았다.
- `retain-plan1/result.json`: 별도 prototype에서 4KiB blob 10,000개의 인증을 old/new/old/new 순서로 측정했다. 기존 4,644/4,618ms, prototype 3,212/3,212ms, 각 시작 load1<4다. 약 31% 차이는 **격리 prototype** 결과다. 제품에는 sparse 처리를 추가했으며 패키지 전체 IMPORT 개선율로 사용하지 않는다.

retention 제품·시험·계약 문서 변경은 `36755bf`에 기록했다. 현재까지 재빌드 후보의 영향 영역 검증, medium/large smoke-2와 최종 20회 게이트는 **NOT RUN**이다. 이전 후보의 부하 위반·목표 미달 기록은 유지한다.
