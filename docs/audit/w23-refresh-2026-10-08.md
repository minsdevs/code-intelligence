# w23 — medium refresh 잔여 병목

- 공개 기준 `6ddeefb`(PR #110), 진단 후보 `XPhUTE`, 후보 product source `be698cc`, baseline `tZgvV7`.
- 통합 작업트리 calm-meadow, 브랜치 `release/gate-followup-20261008`.
- 증거: `validation/local/w23-refresh/`; DB 대상 시험은 `validation/local/w22-persistence/w23-contains-*`.
- 아래 수치는 **원인 진단과 변경 경로 검증**이다. 재빌드한 패키지의 refresh 30초, large 600초 또는 최종 20회 게이트 통과를 뜻하지 않는다.

## 기존 패키지 관측

`profile3/virtual-stack-facts.json`은 계측한 실제 패키지 실행 `TsY7ff`의 원본 virtual-thread dump를 요약한다. initial 122,505ms, refresh 88,704ms이며 refresh의 IMPORT 24,699ms, SOURCE_PARSING 15,301ms, GRAPH_BUILD 21,948ms, TS_PARSING 21,087ms다. 계측 비용이 있으므로 출시 성능 판정에는 쓰지 않는다.

refresh job 표본에는 FILE→type 연결의 PostgreSQL 대기 9개, 소스 retain 응답 대기 6개, TS 첫 analyze 응답 대기 5개가 있다. 표본 개수는 wall time이 아니다. SOURCE_PARSING과 TS_PARSING의 저장 SQL 대기도 관측됐다. Java refresh 로그의 framework parsed 17/reused 4,479, Java analyzer parsed 51/reused phases 13,437을 확인했다. 따라서 이 후보의 지연을 Java 전체 재파싱으로 단정하지 않는다.

## 새 snapshot의 FILE 연결 계획

`GraphBuildStep.linkFileContainsTypes`가 canonical FILE의 natural key와 현재 파일 경로를 비교할 때, 새 snapshot의 통계가 없으면 넓은 snapshot index를 반복 스캔할 수 있었다.

소유권·automation marker·backend PID·후보 hash를 대조한 **합성 workload 전용** PostgreSQL 디렉터리만 새 진단 디렉터리에 COW 복제했다. 프로필의 `secrets.enc`·Keychain·계정 API에는 접근하지 않았다. 패키지의 PostgreSQL 16.15를 private Unix socket에서 실행했고 TCP listener는 만들지 않았다. source inventory digest와 복제본 일치, 원본의 사전·사후 불변, postmaster 종료를 검증했다.

최종 통계가 있는 DB에서는 `native-plan2`의 기존 SQL도 139–209ms였으며 병목이 재현되지 않았다. `native-plan3`은 트랜잭션 안에 새 snapshot과 실제 합성 파일 10,000개·노드 182,214개를 복사해 새 snapshot 통계가 없는 상태를 만들었다. 각 시나리오는 rollback했다.

| SQL | EXPLAIN ANALYZE 실행 시간 | 결과 행 | 측정 직전 load1 |
| --- | ---: | ---: | ---: |
| 기존 natural-key 연결 | 80,022.192ms | 12,836 | 3.8730 |
| 파일 ID 동일성 조건 추가 | 283.998ms | 12,836 | 3.3901 |

기존 계획은 inner scan 12,836회와 join-filter 제거 60,792,001행을 기록했다. 변경 계획은 기존 `uq_graph_nodes_snapshot_natural_key` index를 이용했다. 새 index, migration, 전역 planner 설정은 추가하지 않았다. 이는 동일 진단 DB의 실행 계획 비교이며 실제 앱 GRAPH_BUILD가 80초였다는 뜻은 아니다.

제품 변경은 `and fnode.file_id = tnode.file_id` 한 줄이다. snapshot·FILE type·canonical natural key·허용 type 조건은 유지한다. 파일 ID만 같고 natural key가 다른 FILE alias를 연결하지 않는다.

검증:

- `w23-contains-red`, `w23-contains-shape-red`: 기존 SQL의 Docker 재현 시도였지만 **둘 다 PASS하여 성능 실패를 재현하지 못했다**. 실패로 바꾸어 보고하지 않는다. 큰 비재현 fixture는 영구 시험에 남기지 않았다.
- `w23-contains-green`: 실제 PostgreSQL 대상 **3/3 PASS, 실패/error/skip 0**. `GraphPersistenceLookupPlanTest` 2개와 `GraphPersistenceRoundTripTest` 1개다.
- 새 영구 시나리오는 현재 snapshot의 canonical FILE만 CLASS/DB_ENTITY에 연결하고, 다른 snapshot·FILE alias·METHOD가 포함되지 않음을 검증한다. 기존 lookup budget와 1,200개 노드·중복 metadata·2,401개 edge round-trip도 통과했다.
- `native-plan1`의 provenance assertion 실패는 DB 복제/시작 전 발생했다. 이 실패와 두 비재현 시도, 모든 원본 계획·SQL·로그를 보존한다.

## retained source 인증의 bounded 동시 읽기

기존 retain은 최대 128개 참조의 blob을 순차적으로 열고 인증했다. `desktop/src/source-vault.cjs`는 기존 소유권·경로·파일 identity·AEAD·key ID 검사를 그대로 실행하면서 **최대 4개 읽기**만 함께 진행한다. staged write를 먼저 flush하고 기존 작업 queue 직렬화도 유지한다. 읽은 plaintext buffer는 각 작업의 finally에서 지운다.

한 읽기가 실패해도 같은 그룹의 나머지 읽기를 모두 회수한 뒤 입력 순서의 첫 오류를 반환한다. close/후속 queue 작업은 진행 중인 읽기를 추월하지 않는다. sparse 참조 배열도 기존처럼 실패하며 빈 원소를 성공으로 세지 않는다. protocol·파일 형식·hard limit·Keychain 동작은 변경하지 않았다.

검증:

- `retain-target.log`: source-vault/batch/backup/Windows abstraction/source-broker 대상 **158/158 PASS, 실패/skip 0**. Windows 패키지를 실행했다는 뜻은 아니다.
- `retain-smoke-result.json`: 실제 제품 모듈로 합성 파일 256개 stage→retain→정확한 byte readback. 마지막 ciphertext 변조 거부, close/reopen 후 정상 blob 읽기와 변조 blob 재거부 확인. 실제 Keychain 대신 합성 wrapping만 사용했다.
- `retain-early-rejection-red.log`: 조기 reject mutant가 새 drain/close 시험에서 의도대로 실패했다.
- `retain-sparse-ack-red.log`: sparse 원소를 건너뛰는 mutant가 기존 invalid-input 시험에서 의도대로 실패했다. 두 mutant는 제품 파일을 수정하지 않았다.
- `retain-plan1/result.json`: 별도 prototype에서 4KiB blob 10,000개의 인증을 old/new/old/new 순서로 측정했다. 기존 4,644/4,618ms, prototype 3,212/3,212ms, 각 시작 load1<4다. 약 31% 차이는 **격리 prototype** 결과다. 제품에는 sparse 처리를 추가했으며 패키지 전체 IMPORT 개선율로 사용하지 않는다.

retention 제품·시험·계약 문서 변경은 `36755bf`에 기록했다. 이 커밋 시점에는 재빌드 후보의 영향 영역 검증, medium/large smoke-2와 최종 20회 게이트가 **NOT RUN**이었다. 이전 후보의 부하 위반·목표 미달 기록은 유지한다.

## 그래프 저장의 실제 SQL 묶음 처리

`GraphPersistenceService`의 node/edge 저장을 JDBC의 행별 batch에서 최대 500개 VALUES를 사용하는 SQL로 바꿨다. 같은 묶음에 중복 키가 들어오면 먼저 flush하여 기존 순차 업데이트 의미를 보존한다. node metadata는 기존처럼 병합하고, edge confidence/metadata는 마지막 값으로 대체한다. AMBIGUOUS 처리와 nullable file/line 값의 기존 정책도 유지한다. 반환 ID는 natural key로 대응시키며 PostgreSQL 반환 행 순서에 의존하지 않는다. 간선은 전체 입력을 매개변수 객체로 복사하지 않고 한 묶음씩 저장한다. 전역 JDBC rewrite 옵션은 변경하지 않았다.

- `validation/local/w22-persistence/w23-bulk-green`: **11/11 PASS, 실패/skip 0**. 중복·nullable 값, ID/evidence 연결, 재저장, 새 snapshot 연결, lookup 계획, 실제 Java 증분 pipeline을 확인했다. 일반 test 태스크가 제외하는 ReactRouteBindingIntegrationTest는 이 실행에 포함되지 않았으며 통과 수에 넣지 않는다.
- `native-jdbc-old-correctness`, `native-jdbc-new-correctness`: 제품의 실제 GraphPersistenceService를 패키지 PostgreSQL 16.15의 별도 합성 DB 복제본에서 실행했다. **node 182,214개, edge 317,483개의 canonical 전체 내용이 원본 및 변경 전후에 일치**했다. file ID는 경로로, edge endpoint ID는 natural key로 정규화한 전체 행의 SHA-256을 비교했다. rollback, 원본 snapshot 불변, 원본 PostgreSQL 디렉터리 hash 불변과 정상 서버 종료를 각각 확인했다. 소유권을 검증한 합성 복제본의 private socket 및 임시 loopback 포트만 사용했다. TLS/패키지 E2E 성능 검증은 아니다.
- 이 두 정합성 실행은 시간을 재지 않은 `NOT_RUN_CORRECTNESS_ONLY`다. 따라서 SQL 변경의 속도 개선율이나 출시 SLO 통과를 주장하지 않는다. 기존 StatementCounter는 JDBC execute 호출을 세며 네트워크 왕복 측정기가 아니라는 설명으로 바로잡았다.
- `native-jdbc-old-first`: 최초 시간 측정 시도는 30분 동안 부하 조건을 얻지 못해 persist 호출 **전**에 종료됐다. `NOT_RUN_QUIET_TIMEOUT`과 원본 결과를 보존한다. 해당 구간의 pmset 기록에서 실제 Sleep/Wake/DarkWake 이벤트는 0개였으며, 절전 실패로 분류하지 않는다.

정합성 비교 node hash: `39fde290f209eebdfc3cdb809d7d491692736a6161f0719ea3e7924c41f338f7`. edge hash: `996dff64e0aec386fde53d722fb6bd4496946e109fdeda7138a79f9002af6df1`.

## 본문 secret 검사에서 불필요한 정규식 순회 제거

`LocalSourcePolicy`의 기존 여섯 signature와 assignment 정규식은 바꾸지 않았다. 현재 모든 규칙에 반드시 존재하는 literal이 전혀 없는 본문만 한 번의 allocation-free 순회로 걸러낸다. marker가 있으면 기존 정규식·placeholder 예외·source/config의 unquoted 처리 규칙이 최종 판정한다. 본문 읽기·hash·소유권 검사·크기 제한은 생략하지 않는다. 향후 signature나 assignment 이름을 추가할 때는 보수적인 marker 범위도 함께 갱신해야 한다.

- `policy-green-2/test-totals.json`: 실제 import/fingerprint·binding·secret corpus **198/198 PASS, 실패/skip 0**. 기존 파일 뒤쪽 credential 시험을 20개 signature/assignment 사례로 확장했다.
- `policy-green-2/accuracyTest-totals.json`: 실제 loopback TypeScript analyzer와 PostgreSQL을 사용하는 React route binding **5/5 PASS, 실패/skip 0**. 일반 test에서 제외된 시험을 전용 accuracyTest로 실행했다.
- `policy-product-first/result.json`: 변경 전/후 실제 제품 클래스를 별도 classloader로 불러 source/config 두 모드에서 **45,940개 판정 일치**를 확인했다. 합성 medium 파일 10,000개(52,428,800 bytes), signature 길이 경계·대소문자·뒤쪽 위치·placeholder·Unicode/random 사례를 포함한다. 입력 fixture와 제품 class hash 불변도 확인했다.
- 같은 파일 집합을 old/new/old/new 순서로 측정했다. 기존 **2,544/2,540ms**, 제품 변경 후 **216/222ms**였으며 모든 시작 load1은 4 미만이었다. 이 합성 집합에는 marker가 있는 파일이 0개였다. 따라서 빠른 경로의 효과만 확인한 것이며 일반 저장소나 전체 IMPORT/refresh의 개선율로 일반화하지 않는다. 앞선 `policy-prototype-first` 결과도 보존한다.
- 최초 `policy-green`은 **197 PASS / 1 FAIL**이다. 실제 Unix socket fixture가 긴 작업트리의 절대 경로 제한에 걸려 정책 검증 전에 실패했다. 같은 fixture를 더 짧은 CWD-relative 주소로 bind하도록 고쳤으며 socket 거부·기존 저장소 보존 assertion은 유지했다. 실패 시험부터 `w23-policy-socket-green`에서 **1/1 PASS**를 확인한 뒤 전체 대상 시험을 다시 실행했다. 최초 실패를 통과로 덮어쓰지 않았다.

이 결과는 대상 정확성·격리 진단의 증거다. 새 패키지 회귀와 medium/large smoke-2, 최종 20회 판정은 별도이며 기존 실패 및 NOT RUN 항목을 대체하지 않는다.

## 통합 후보의 후속 검증

이 문서의 유닛별 NOT RUN은 각 진단·커밋 시점의 기록이다. 이후 제품 소스 `a04fa4d`에서 만든 KOwFxr의 통합 회귀와 영향 영역 패키지 검증은 [별도 후보 감사](candidate-kowfxr-2026-10-09.md)에 기록한다. 이 연결은 기존 실패를 통과로 바꾸거나 격리 진단을 최종 성능 수용으로 승격하지 않는다.
