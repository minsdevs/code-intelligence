# Native owner leases for interrupted desktop maintenance

This is a trusted-main ownership primitive for `purpose-keyring`, `ai-journal`, and `source-vault`.
It changes no key, journal, source envelope, financial event, database, or recovery-record format.
The optional native mode supersedes the **owner-lock behavior only** in the earlier primitive
contracts. Callers that omit `ownerLocks` retain the existing exclusive-create legacy behavior.

## Problem and scope

The legacy main-process modules create an `O_EXCL` lock file and unlink it at orderly closure.
A killed main leaves the file behind. PID existence and elapsed time cannot establish ownership,
and deleting it could admit a second writer. This is a recovery availability defect, not evidence
that a second legacy writer could bypass the existing lock.

The new mode leaves an immutable native-v2 marker and holds an OS `FileChannel.tryLock()` lease
on its inode in a narrow JVM worker. Main owns the worker's stdin pipe. Main termination closes
the pipe; EOF ends the worker and releases the OS lease. Opening the *same validated marker*
afterwards does not initialize keys or alter retained B history.

This primitive assumes Electron main holds `app.requestSingleInstanceLock()` for the same
`userData`, and that every participating B writer belongs to that main. Root main must enforce
`ownsInstance && app.hasSingleInstanceLock()` and synchronously stop admission when `onLost`
runs. The helper holds the OS lock; Node performs B writes. A helper-only SIGKILL releases that
lock before Node necessarily observes exit. Consequently the helper alone is **not atomic
cross-process writer fencing**. The Electron ownership premise and fail-closed main lifecycle
are required; arbitrary Node callers cannot obtain an equivalent guarantee by asserting `true`.

## Main-only API

```js
const ownerLocks = await createNativeOwnerLocks({
  javaPath, jarPath, safetyRoot, installationId,
  assertMainOwnership: () => ownsInstance && app.hasSingleInstanceLock(),
  onLost: error => stopAdmissionsAndCloseOwnedRuntime(error),
  timeoutMs: 10000, // optional, 50..30000 ms
});

const keys = await openPurposeKeyring({ ...keyOptions, ownerLocks });
const journal = await openSafetyJournal({ ...journalOptions, ownerLocks });
const source = await openSourceVault({ ...sourceOptions, ownerLocks });
// Also accepted by explicit initialize factories and openSourceVaultRestoreStage.

// Drain all owning modules first. Source/backup closes before journal, then keyring.
await source.close();
await journal.close();
await keys.close();
await ownerLocks.close();
```

`createNativeOwnerLocks` returns a frozen, locally branded `{close()}` facade. Creation validates
the existing private parent and pins the Java/JAR paths and file states; it creates no directory,
marker, key, or journal. Missing B/role directories are never inferred to mean a fresh install.
The caller must use the existing explicit enrollment/recovery checks before any initialize call.

Internal module import `acquireNativeOwnerLock(provider, {safetyRoot, installationId, kind})`
requires that brand, the factory's exact root/installation and a fixed role. It returns internal
`{check(), isHeld(), release()}` functions; these and the provider never cross renderer IPC,
HTTP, environment, backend bridge or an archive. `isHeld()` is a synchronous known-loss check,
not a fresh OS acknowledgement. `check()` serializes a worker round trip and rechecks paths.
The optional `spawnImpl` is trusted dependency injection used only by synthetic protocol tests;
production main uses the built-in fixed launcher. It is not an untrusted extension/plugin port.

| Role | Sole marker | Protected module |
| --- | --- | --- |
| `purpose-keyring` | `safetyRoot/purpose-keyring/owner.lock` | Purpose key reads/rotation |
| `ai-journal` | `safetyRoot/ai-journal/writer.lock` | Safety journal/latch operations |
| `source-vault` | `safetyRoot/source-vault/owner.lock` | Shared source keys and one live/staged source store |

There is no caller-selected marker path. Source export and restore staging acquire the same B
role, so one cannot overlap the other. The provider does not attest an arbitrary `sourceRoot`:
the existing vault path checks and main's fixed-live/owned-stage authority remain mandatory.
Source keys are neither exported nor regenerated by this mode.

## Persistent marker and worker protocol

Each marker is exactly ASCII `CI-NATIVE-OWNER-2\n`, then SHA-256 of the installation ID, newline,
the fixed role, newline. It contains no PID, time, credential, key, source text or user path.
New markers use exclusive creation and mode 0600. Existing markers must already have the exact
version, role and installation binding. They are never truncated, overwritten, renamed, deleted
or repaired. Directories must be canonical, owned 0700; markers must be regular, owned 0600,
single-link files. Symlinks, special files, wrong owner/mode, changed inode/state and oversized
markers fail closed. All three markers remain on normal close.

The JVM worker is `dev.codeintelligence.desktop.NativeLeaseWorker`, invoked by the packaged
backend entrypoint as `java -jar <fixed JAR> --ci-desktop-lease` **before Spring starts**.
Malformed/prefixed lease flags also enter the worker and are rejected rather than starting Spring.
The entrypoint also dispatches the separately owned `ManagedProcessWorker`; that worker's
process-management behavior is not authored or certified by this lease change.

Stdin carries one bounded ASCII ACQUIRE frame (canonical base64url UTF-8 root, installation,
role and random challenge); after acquisition, strictly increasing CHECK/RELEASE sequence IDs
receive exact HELD/RELEASED replies. The root is not argv or environment. No application secret
or key enters the helper. Responses are bounded and unexpected bytes, duplicate/trailing replies,
stderr, exit, EOF during a request, timeout or wrong sequence poison the lease.

READY follows OS acquisition, marker file fsync when newly created, directory fsync and exact
marker/path readback. Existing markers are only read and locked. RELEASED is sent after release;
Node additionally waits for actual clean process closure before acknowledging release. Missing
closure is a failure and the helper is terminated. Closing a provider with an acquisition or
lease still active rejects BUSY; it cannot silently release locks beneath live modules.

The launcher resolves and pins trusted Java/JAR paths and file metadata, uses `shell:false`,
and an environment allowlist that excludes Java injection variables. This supplements the
runtime bundle's authenticity checks; it is not a replacement for code signing or artifact hashes.

## Failure and restart rules

1. The worker can reopen only an already valid native-v2 marker, or exclusively create one
   when the marker is absent in an existing validated module directory.
2. A live lock in another process rejects. Duplicate acquisition of one role in one provider
   rejects before spawning another helper. Releases/checks are ordered inside each lease.
3. Legacy v1 locks, including apparently dead/high-PID locks, reject unchanged. Legacy writers
   did not participate in the OS lease, so absence of an OS holder cannot prove them dead.
4. A **cleanly closed** legacy module has no marker and can enroll native-v2 on its next explicit
   open while retaining existing authenticated keys/history. Older code then encounters the
   persistent marker and fails its legacy exclusive-create acquisition.
5. Helper or singleton loss is sticky for the entire provider. A once-only static `onLost` reason
   reaches trusted main. Keyring reads/rotation, journal actions and source operations subsequently
   reject. Journal diagnostic snapshots are OFF/recovery-only after observed loss. Journal poison
   fallback cannot write a latch without its native lease.
6. Writes check ownership before publication and before success acknowledgement. Journal checks
   precede log writes and activation-latch removal. Key/source atomic writers recheck immediately
   before rename and after durability; owned temporary cleanup does not delete published targets.
7. Node main SIGKILL causes helper EOF. A later authorized main can authenticate/replay existing
   B and reopen sources using the same marker inode and retained keys. Journal replay retains its
   established restart-OFF event and liability semantics; it does not activate AI.
8. Interrupted **first marker creation** may leave a partial marker. It is rejected, not reset.
   Torn journal frames, pending ciphertext, missing keys and other pre-existing ambiguous state
   keep their original recovery blockers. This is not arbitrary byte-level crash repair.

No PID probe, age threshold, stale-lock unlink, automatic re-enrollment, B deletion, credential
fallback, DB access, keychain access, provider call or paid action is part of the primitive.

## Verification and limits

Synthetic tests compile this one worker using `javac --release 21`, build a tiny standalone JAR,
then exercise **real local OS file locks** and child processes. Test wrapping is authenticated
encryption under a public fixture key, not the actual OS keychain. The SIGKILL integration holds
all three roles in a real Node child, preserves a reserved liability and source object, kills the
owner, then checks retained key fingerprint, same marker inode, old journal prefix/liability,
restart OFF and original source data after reopening.

Further tests cover competing JVMs, same-provider races, release ordering, legacy/torn/unknown
markers, cross-installation binding, unsafe paths/FIFO, marker/directory replacement, helper and
singleton loss, pre-publication faults, source stage serialization and retained rotation keys,
bounded protocol failures/timeouts, actual close after RELEASED, launcher environment, and pinned
binary mutation. The final author manifest/log/XML is recorded separately under
`/tmp/ci-backup-resume-lock-*`; earlier `ci-ai-*` and `ci-backup-*` frozen evidence is unchanged.

Not established here: packaged JRE/JAR launch, full Spring build, Electron single-instance behavior
on real application startup, actual OS keychain, real user DB/source recovery, signing/distribution,
physical power-loss durability, network filesystems, or the managed PG/Redis/backend child guardian.
In particular **a B lease does not prove an orphan PostgreSQL child is owned**. Main must finish
the separately verified service-guardian and durable recovery-marker checks before product resume.
No lock primitive repairs a lost device key, accepts unknown B state, or establishes rollback
resistance against a malicious process with the same user's filesystem rights. Pathname checks
and JVM file attributes are not native directory-fd confinement against adversarial ancestor swaps.

The implementation author also wrote these regressions. Independent review and root's final
main/runtime/build gates remain separate acceptance evidence; test success alone is not a product
release or backup/restore Go decision.
